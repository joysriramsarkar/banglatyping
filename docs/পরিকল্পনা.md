এই রিপোজিটরিতে সবচেয়ে গুরুত্বপূর্ণ সমস্যা হলো নিরাপত্তার নকশা এবং বাস্তব database client-এর আচরণের মধ্যে অসংগতি। README বলছে ব্যবহারকারীর access token database পর্যন্ত পাঠানো হয়, যাতে Row Level Security বা RLS কাজ করে। কিন্তু দেখা src/lib/db.ts কোডে service key পাওয়া গেলে createRequestClient() ব্যবহারকারীর token-ভিত্তিক client-এর বদলে admin client ফেরত দেয়। ফলে application-এর স্বাভাবিক request-এ database-এর দ্বিতীয় স্তরের ownership protection এড়িয়ে যাওয়ার পথ তৈরি হয়েছে। এটি সবার আগে সংশোধন করা দরকার। README Database client

৩. সবচেয়ে গুরুতর বিষয়: user request-এ service-role client ব্যবহার
৩.১ বাস্তবে কী দেখা গেছে

src/lib/db.ts-এ getSupabaseAdmin() service key ব্যবহার করে একটি client তৈরি করে। এরপর createRequestClient() শুরুতেই সেই admin client নেয়। সেটি পাওয়া গেলে user access token যাচাই বা forward করার আগেই admin client ফেরত দেয়। সংশ্লিষ্ট অংশ:

``ts
export function createRequestClient(accessToken?: string | null): ReturnType<typeof createClient> {
  const admin = getSupabaseAdmin();
  if (admin) {
    return admin;
  }

  if (!accessToken) {
    return getSupabase();
  }

  return createClient(supabaseUrl, supabaseKey, {
    global: {
      headers: { Authorization: Bearer ${accessToken} },
    },
    auth: {
      persistSession: false,
`

এটি দেখা source excerpt থেকে নেওয়া। মূল সমস্যা হলো privilege নির্বাচন user request-এর প্রকৃত প্রয়োজন অনুযায়ী হচ্ছে না; environment-এ service key আছে কি না, তার ওপর হচ্ছে। Database client

৩.২ কেন এটি বিপজ্জনক

ধরা যাক, একটি progress endpoint authentication যাচাই করে। কিন্তু পরবর্তী query-তে developer ভুল করে owner filter দিতে ভুলে গেলেন।

সঠিকভাবে configured user-scoped client হলে RLS অতিরিক্ত সুরক্ষা দিতে পারে। Admin client ব্যবহৃত হলে সেই প্রতিরক্ষা আর স্বাভাবিকভাবে পাওয়া যায় না।

এখানে authentication এবং authorization-এর পার্থক্য গুরুত্বপূর্ণ:

• Authentication: request পাঠানো ব্যক্তিটি কে?
• Authorization: তিনি কোন resource পড়তে বা পরিবর্তন করতে পারবেন?
• Database isolation: application code-এ ভুল হলেও database কি অন্যের row আটকে দেবে?

শুধু প্রথমটি নিশ্চিত করলেই দ্বিতীয় এবং তৃতীয়টি নিশ্চিত হয় না।

৩.৩ কী দাবি করা যাচ্ছে না

সব endpoint পড়া হয়নি। তাই বর্তমানে যে কেউ অন্যের তথ্য পড়তে পারে, এমন সিদ্ধান্ত দিচ্ছি না।

যা নিশ্চিতভাবে বলা যায়: service key উপস্থিত থাকলে এই helper-এর নাম এবং README-তে বর্ণিত user-scoped security model-এর সঙ্গে তার আচরণ মেলে না। ফলে endpoint-level authorization-এ ছোট ভুলের সম্ভাব্য ক্ষতি বেড়ে যায়।

৩.৪ প্রয়োজনীয় সংশোধন

এই application-এর database access-কে তিনটি স্পষ্ট শ্রেণিতে ভাগ করুন:

• Public read client: প্রকাশ্য lesson বা public content পড়ার জন্য।
• Authenticated user client: ব্যবহারকারীর token নিয়ে নিজের progress, settings এবং session data ব্যবহারের জন্য।
• Privileged admin client: seed, migration support, নির্দিষ্ট administrative operation-এর জন্য।

কোনো সাধারণ user-request helper-এর মধ্যে automatic admin fallback রাখবেন না।

উদাহরণস্বরূপ API design এমন হতে পারে:

`ts
createPublicReadClient()
createAuthenticatedUserClient(accessToken)
createPrivilegedAdminClient()
`

এগুলো প্রস্তাবিত interface, repository-তে থাকা function-এর দাবি নয়।

এই নামকরণ একাই security তৈরি করবে না, কিন্তু code review সহজ করবে। Reviewer তখন privileged operation কোথায় হচ্ছে, দ্রুত ধরতে পারবেন।

৩.৫ Acceptance criteria

এই সংশোধন শেষ হয়েছে বলার জন্য অন্তত নিচের আচরণ পরীক্ষা করা উচিত:

• Service key থাকলেও সাধারণ user endpoint user-scoped client ব্যবহার করে।
• Token না থাকলে protected operation fail করে; silently public বা admin mode-এ যায় না।
• User A-এর token দিয়ে User B-এর row পড়া বা update করা ব্যর্থ হয়।
• Route-এর owner filter ভুল হলেও RLS দ্বিতীয় প্রতিরক্ষা হিসেবে কাজ করে।
• Privileged operation আলাদা module এবং explicit authorization-এর মধ্যে থাকে।
• Authorization failure debug করার জন্য admin fallback চালু করার প্রয়োজন না হয়।

এটি এই repository-র সবচেয়ে আগে নেওয়ার মতো সংশোধন।

৪. README-এর security description বাস্তব implementation-এর সঙ্গে মিলছে না

README বলছে API caller-এর token createRequestClient দিয়ে data layer-এ পাঠানো হয়, যাতে RLS policy কার্যকর থাকে। README আরও বলছে service key server-side seed এবং diagnostic script-এর জন্য ব্যবহৃত হয়। কিন্তু দেখা database client-এ service key application request-এর client selection-এও অংশ নিচ্ছে। Documentation এখানে ভুল নিরাপত্তাবোধ তৈরি করতে পারে। README Database client

• Service-role ব্যবহারের তালিকা রাখুন: কোথায় প্রয়োজন, কেন প্রয়োজন, কীভাবে সীমাবদ্ধ।

৬. userid-এর legacy text schema পুনর্বিবেচনা করা দরকার

RLS migration-এর মন্তব্যে বলা হয়েছে userid column VARCHAR(255) এবং এটি আগের Firebase-ভিত্তিক schema-এর অবশিষ্টাংশ। Supabase auth user ID রাখার জন্য ::text cast ব্যবহার করা হচ্ছে। এটি সরাসরি vulnerability নয়, কিন্তু schema semantics দুর্বল করার সম্ভাবনা আছে। RLS migration

UUID-ভিত্তিক identity ব্যবহারের সিদ্ধান্ত নিলে database-এও সেই intent প্রকাশ করা ভালো। তবে “সব text ID এখনই UUID করে ফেলুন” বলা দায়িত্বশীল পরামর্শ হবে না; existing data, guest identity এবং external imports দেখতে হবে।

সংশোধনের সঠিক ক্রম:

• বর্তমান data profile করুন: সব ID বৈধ UUID কি না।
• Identity model লিখুন: guest এবং authenticated user কীভাবে আলাদা হবে।
• Orphan data খুঁজুন: কোনো progress row-এর owner অনুপস্থিত কি না।
• Foreign-key policy নির্ধারণ করুন: account delete হলে কী হবে।
• Migration rehearsal করুন: production copy নয়, নিরাপদ test fixture বা sanitized dataset ব্যবহার করে।
• Rollback plan রাখুন: conversion ব্যর্থ হলে কীভাবে ফিরবেন।

প্রয়োজনে staged migration ব্যবহার করুন। আগে নতুন column, তারপর backfill, তারপর validation, তারপর application cutover।

আরও গুরুত্বপূর্ণ প্রশ্ন: account deletion-এর পর practice history, certificate এবং analytics কী হবে? ON DELETE CASCADE দিলেই product decision শেষ হয় না।

৭. Environment configuration এখন অতিরিক্ত নরমভাবে ব্যর্থ হচ্ছে

Database client-এ public Supabase URL বা key না থাকলে warning দেওয়া হচ্ছে:

`ts
if (!supabaseUrl || !supabaseKey) {
  console.warn('⚠️ Supabase credentials not fully configured');
}
`

এরপর client creation-এর চেষ্টা হতে পারে। Misconfiguration আগেভাগে নির্দিষ্টভাবে ধরা না পড়লে পরে অস্পষ্ট runtime failure তৈরি হয়। Database client

এখানে TypeScript-এর non-null assertion ব্যবহৃত হলেও runtime environment variable তৈরি হয়ে যায় না। Compiler-কে আশ্বস্ত করা এবং production configuration যাচাই করা এক বিষয় নয়।

৭.১ উন্নত আচরণ

Configuration-কে context অনুযায়ী যাচাই করুন:

• Browser configuration: শুধু প্রকাশযোগ্য URL এবং public key।
• Server user-request configuration: user-scoped access-এর জন্য যা প্রয়োজন।
• Privileged script configuration: service key প্রয়োজন হলে কেবল সেখানে বাধ্যতামূলক।
• Build configuration: build-এর সময় আসল database connection প্রয়োজন কি না, স্পষ্ট সিদ্ধান্ত।

প্রতিটি mode-এ প্রয়োজনীয় variable অনুপস্থিত হলে actionable error দিন।

উদাহরণ:

`text
Missing required server configuration: SUPABASESERVICEKEY.
This command requires privileged database access.
`

এটি administrative command-এর error হতে পারে। সাধারণ typing page-এর জন্য service key বাধ্যতামূলক করা উচিত নয়।

৭.২ কী করা উচিত নয়

Secret-এর value log করবেন না। Error-এ variable-এর নাম থাকুক, credential নয়।

একইভাবে production-এ misconfiguration ঢাকতে automatic mock data বা anonymous client-এ fallback করানো যাবে না, যদি তা ব্যবহারকারীকে ভুলভাবে “data saved” দেখায়।

Guest practice আলাদা supported mode হলে সেটি স্পষ্টভাবে design করতে হবে।

৮. Server-only এবং browser-safe database module আলাদা করা দরকার

দেখা db.ts-এ public client এবং service-key client একই module-এ আছে। এতে সরাসরি secret browser-এ গেছে, এমন প্রমাণ নেই। NEXTPUBLIC ছাড়া variable ব্যবহারের অর্থও স্বয়ংক্রিয়ভাবে leak নয়। কিন্তু module boundary অস্পষ্ট হলে ভবিষ্যৎ ভুলের সুযোগ বাড়ে। Database client

সুপারিশ:

• Browser-safe module: public configuration এবং browser auth behaviour।
• Server request module: verified request context এবং user-scoped database access।
• Administrative module: service credential, explicit privileged functions।
• Import restriction: browser code যেন administrative module import করতে না পারে।
• Static check: prohibited imports ধরার ব্যবস্থা।
• Bundle verification: browser artifact-এ secret বা privileged configuration ঢোকেনি তা পরীক্ষা।

এটি শুধু security নয়, developer experience-ও উন্নত করবে। নতুন contributor বুঝতে পারবেন কোন client কোথায় ব্যবহার করা উচিত।

৯. Singleton এবং proxy abstraction অপ্রয়োজনীয় জটিলতা তৈরি করতে পারে

দেখা module-এ cached client এবং Proxy export আছে:

`ts
export const supabase = new Proxy({} as ReturnType<typeof createClient>, {
  get: (, prop) => getSupabase()[prop as keyof ReturnType<typeof createClient>],
});
`

এই implementation দেখেই runtime bug নিশ্চিত করা যায় না। তবে lazy proxy object-এর সুবিধা বনাম debugging cost বিবেচনা করা দরকার। Database client

সম্ভাব্য জটিলতা:

• Initialization timing: error কখন উঠবে তা import দেখে বোঝা কঠিন।
• Method access semantics: client API বদলালে proxy behaviour পরীক্ষা প্রয়োজন।
• Test mocking: shared singleton state test isolation কঠিন করতে পারে।
• Environment switching: configuration module-load time-এ capture হলে test environment পরিবর্তন জটিল হয়।
• Request context: browser singleton এবং server request-scoped client-এর উদ্দেশ্য গুলিয়ে যেতে পারে।

Browser-এ stable auth client রাখা এবং server-এ প্রতিটি authenticated request-এর context আলাদা রাখা দুই ভিন্ন প্রয়োজন।

সুপারিশ: স্পষ্ট factory বা getter ব্যবহার করুন, এবং public convenience abstraction-এর চেয়ে predictable behaviour-কে অগ্রাধিকার দিন।

১০. বাংলা typing-এর মূল সমস্যা: “character” শব্দের অস্পষ্ট ব্যবহার

প্রকল্পের grapheme documentation-এ বলা হয়েছে mapping fix করা হয়েছে, কিন্তু typing validation এখনও character-by-character আছে। একই নথিতে JavaScript string splitting এবং Bengali conjunct handling-এর সমস্যা ব্যাখ্যা করা হয়েছে। এখানে “character” বলতে কী বোঝানো হচ্ছে, তা পরিষ্কার না হলে পুরো scoring model বিভ্রান্তিকর হতে পারে। বাংলা grapheme documentation

বাংলা typing-এ অন্তত পাঁচটি আলাদা স্তর রয়েছে:

• UTF-16 code unit: JavaScript string indexing-এর ভিত্তি।
• Unicode code point: অক্ষর বা combining mark-এর encoded unit।
• Grapheme cluster: segmentation অনুযায়ী একটি একত্রে ধরা text unit।
• Orthographic unit: বাংলা ভাষার লিখনরীতিতে অর্থপূর্ণ গঠন।
• Keystroke sequence: keyboard layout অনুযায়ী চাপা key-এর ধারাবাহিকতা।

এই পাঁচটি এক নয়।

১০.১ কেন mapping fix যথেষ্ট নয়

ধরা যাক virtual keyboard সঠিক key sequence দেখাচ্ছে। তবু application যদি cursor movement, error highlighting, progress count বা backspace handling-এ UTF-16 index ব্যবহার করে, ব্যবহারকারীর সামনে অসংগত আচরণ হতে পারে।

অর্থাৎ সঠিক key hint এবং সঠিক text validation দুটি পৃথক সমস্যা।

১০.২ প্রয়োজনীয় specification

প্রথমে লিখিতভাবে নির্ধারণ করুন:

• Matching unit: raw code point, normalized text, না grapheme sequence?
• Progress unit: কতটুকু লেখা হলে কত শতাংশ complete?
• Error unit: ভুল key, ভুল grapheme, না ভুল word?
• Deletion unit: backspace-এ কী মুছবে?
• WPM unit: কোন text length থেকে হিসাব হবে?
• Composition rule: অসম্পূর্ণ input কবে validation-এর বাইরে থাকবে?

এই সিদ্ধান্ত ছাড়া utility যোগ করলে বিভিন্ন component ভিন্ন ব্যাখ্যা অনুসরণ করতে পারে।

১১. Grapheme documentation-এর কিছু ব্যাখ্যা আরও নির্ভুল হওয়া প্রয়োজন

দেখা documentation-এ 'ষ্ট্র'-এর প্রসঙ্গে একাধিক হসন্ত এবং ZWJ থাকার কথা বলা হয়েছে। এই যুক্তাক্ষরটিতে ZWJ থাকা বাধ্যতামূলক নয়; সাধারণ character sequence দিয়েও এটি লেখা যায়। নির্দিষ্ট input-এ joiner থাকলে সেটি আলাদা fixture হিসেবে দেখানো উচিত। বাংলা grapheme documentation

আরেকটি সূক্ষ্ম বিষয়: সাধারণ বাংলা code point-গুলোর অনেকই UTF-16-এর একটি code unit-এ represented হয়। সমস্যা শুধু “প্রতিটি বাংলা অক্ষর multi-codeunit” নয়; বরং চোখে এক গঠন হিসেবে দেখা অংশ একাধিক code point বা combining sequence দিয়ে তৈরি হতে পারে।

Documentation সঠিক না হলে future implementation ভুল mental model অনুসরণ করতে পারে।

উন্নয়ন করুন এভাবে:

• Visible text-এর সঙ্গে code point sequence দিন।
• ZWJ আছে এবং নেই, এমন fixture আলাদা করুন।
• Canonical equivalence এবং visual similarity আলাদা ব্যাখ্যা করুন।
• Grapheme cluster এবং বাংলা শেখানোর unit সবসময় সমান নয়, এটি লিখুন।
• Expected output স্পষ্ট করুন: শুধু “সঠিক boundaries অনুযায়ী” না লিখে নির্দিষ্ট segmentation result দিন।
• Documentation example-কে automated test-এর সঙ্গে মিলিয়ে রাখুন।

এতে ভাষাতাত্ত্বিক এবং programming-level ব্যাখ্যার মধ্যে দূরত্ব কমবে।

১২. Unicode normalization policy আবশ্যক

Typing app-এ একইভাবে দেখা text-এর encoding সবসময় একই নাও হতে পারে। তাই normalization policy নির্ধারণ করা জরুরি।

তবে সবকিছুর ওপর নির্বিচারে normalization প্রয়োগ করাও ঠিক নয়। Raw input, display representation এবং scoring representation-এর উদ্দেশ্য ভিন্ন হতে পারে।

১২.১ প্রস্তাবিত নীতি

একটি পরিষ্কার pipeline রাখুন:

`text
Raw input
  -> composition handling
  -> policy-based normalization
  -> segmentation
  -> comparison
  -> scoring
  -> feedback
`

এটি প্রস্তাবিত architecture, বর্তমান implementation-এর বর্ণনা নয়।

Raw text সংরক্ষণ প্রয়োজন কি না privacy এবং debugging requirement অনুযায়ী ঠিক করুন। শুধু scoring-এর জন্য দরকার হলে সম্পূর্ণ keystroke history server-এ পাঠানোর প্রয়োজন নেই।

১২.২ কী এড়িয়ে চলবেন

Visually similar সব character-কে একই বানিয়ে দেওয়া উচিত নয়। তাতে প্রকৃত spelling mistake লুকিয়ে যেতে পারে।

একইভাবে invisible character পেলেই silently বাদ দিলে ব্যবহারকারী কেন score বদলাল বুঝবেন না।

ভালো আচরণ:

• Supported normalization স্পষ্ট থাকবে।
• Unsupported control character শনাক্ত হবে।
• User-facing feedback বোধগম্য হবে।
• Scoring deterministic থাকবে।
• Dataset এবং input একই policy অনুসরণ করবে।

১৩. IME এবং composition event সঠিকভাবে সামলানো অপরিহার্য

এই অংশটি যাচাইযোগ্য requirement, বর্তমান bug-এর নিশ্চিত দাবি নয়। Typing component-এর source দেখা হয়নি।

বাংলা লেখার সময় ব্যবহারকারী একটি physical key press-এর সঙ্গে সঙ্গে final Unicode text নাও পান। Input Method Editor বা phonetic input ধাপে ধাপে text গঠন করতে পারে।

যদি application প্রতিটি মাঝপথের input-কে final answer ধরে, তাহলে সঠিক typing-ও ভুল হিসেবে গণনা হতে পারে।

১৩.১ প্রয়োজনীয় আচরণ

Composition চলাকালে application-এর উচিত:

• Premature error counting বন্ধ রাখা।
• Final committed text-এর অপেক্ষা করা।
• Cursor এবং selection ঠিক রাখা।
• Input rerender করে composition ভেঙে না দেওয়া।
• Composition শেষ হওয়ার পর একবার consistent validation করা।

শুধু keydown-এর ওপর নির্ভর করলে mobile keyboard, IME এবং speech input-এর কিছু behaviour বাদ পড়ে যেতে পারে। আবার শুধু input value দেখলেও physical key drill-এর সব তথ্য পাওয়া যায় না।

এখানেই input method এবং practice mode আলাদা করা দরকার।

১৩.২ Test cases

কমপক্ষে পরীক্ষা করুন:

এগুলো manual browser test এবং automated test মিলিয়ে যাচাই করতে হবে।

১৪. Avro, Bijoy এবং BanglaWord-কে এক ধরনের layout ধরে নেওয়া যাবে না

README-তে তিনটি layout-এর কথা আছে। কিন্তু layout support-এর সংজ্ঞা স্পষ্ট হওয়া দরকার। README

Support বলতে কী বোঝায়?

শুধু virtual keyboard দেখানো, key hint দেওয়া, native OS input গ্রহণ করা, নাকি application নিজেই transliteration করে Unicode text তৈরি করা?

এই চারটি ভিন্ন সক্ষমতা।

১৪.১ Avro-র ক্ষেত্রে বিশেষ বিবেচনা

Phonetic input-এ একাধিক Latin key মিলে একটি বাংলা text segment তৈরি করতে পারে। তাই “এই বাংলা character-এর একটিমাত্র key” ধরনের mapping সব ক্ষেত্রে যথাযথ হবে না।

Lesson hint-এ accepted sequence, partial sequence এবং completed output-এর সম্পর্ক দেখাতে হবে।

১৪.২ Fixed-layout mode-এর বিবেচনা

Fixed layout practice-এ physical key position, Shift state এবং sequence গুরুত্বপূর্ণ হতে পারে। একই final Unicode text লেখা হয়েছে মানেই সঠিক prescribed key sequence অনুসরণ করা হয়েছে, এমন নয়।

তাই free typing score এবং key-sequence drill score আলাদা রাখা যুক্তিযুক্ত।

১৪.৩ আবশ্যক product decision

প্রতিটি mode-এর জন্য লিখুন:

• Input source: native keyboard না internal mapping?
• Validation target: final text না prescribed keys?
• Allowed alternative: অন্য sequence গ্রহণযোগ্য কি না?
• Scoring unit: text output না physical action?
• Comparison group: অন্য layout-এর সঙ্গে rank তুলনা হবে কি না?

এটি না করলে শিক্ষার্থীকে ভুলভাবে দুর্বল বলা হতে পারে।

১৫. WPM এবং accuracy-এর সংজ্ঞা প্রকাশ করতে হবে

এই repository-র actual WPM implementation দেখা হয়নি। তাই formula ভুল, এমন দাবি করছি না। তবে বাংলা typing app-এ metric definition প্রকাশ করা আবশ্যক।

প্রচলিত একটি typing convention হলো নির্দিষ্ট character count-কে একটি standard word ধরে speed গণনা করা। কিন্তু বাংলা ক্ষেত্রে character বলতে code point, grapheme বা অন্য unit বোঝালে ফলাফল বদলে যায়।

১৫.১ কী জানাতে হবে

Result screen বা help text-এ স্পষ্টভাবে জানান:

• Speed calculation unit কী।
• সময় কখন শুরু হয়।
• Idle time ধরা হয় কি না।
• Corrected mistake কীভাবে গণনা হয়।
• Paste করা text-এর নিয়ম কী।
• Different layout-এর score তুলনাযোগ্য কি না।

একটি app-এ precision-এর ভান করা সংখ্যার চেয়ে ব্যাখ্যাযোগ্য metric বেশি মূল্যবান।

১৫.২ Accuracy-র দুটি ভিন্ন অর্থ

একজন ব্যবহারকারী অনেক ভুল করে সব ঠিক করে শেষ করতে পারেন। Final text তখন নিখুঁত, কিন্তু typing process নিখুঁত ছিল না।

তাই প্রয়োজনে আলাদা দেখান:

• Final-text accuracy
• First-pass accuracy
• Correction count
• Error rate

সব একসঙ্গে দেখাতেই হবে, তা নয়। কিন্তু ভেতরে definition আলাদা থাকা প্রয়োজন।

১৫.৩ সময় গণনা

Elapsed duration-এর জন্য wall clock পরিবর্তনের প্রভাব এড়ানোর নীতি থাকতে হবে। Timer tab background-এ গেলে কী হবে, সেটিও স্পষ্ট করুন।

Practice mode-এ pause গ্রহণযোগ্য হতে পারে। Certificate mode-এ একই policy নাও হতে পারে।

একই timer logic সব mode-এ ব্যবহার করলেই সঠিক design হয় না।

১৬. Text comparison algorithm ভুল feedback তৈরি করতে পারে

এটিও পরীক্ষা করতে হবে; actual comparison implementation দেখা হয়নি।

ধরা যাক ব্যবহারকারী একটি অতিরিক্ত character লিখলেন। যদি target এবং input কেবল একই index ধরে compare করা হয়, পরবর্তী সব character ভুল দেখাতে পারে।

এতে ব্যবহারকারী আসলে একটি insertion error করলেও application অনেকগুলো substitution error গণনা করতে পারে।

দুটি mode আলাদা করা ভালো:

• Live guidance: খুব দ্রুত এবং স্থিতিশীল feedback।
• Final analysis: insertion, deletion এবং substitution আলাদা বোঝার জন্য richer comparison।

প্রতিটি keystroke-এ ব্যয়বহুল alignment চালানো প্রয়োজন নেই। কিন্তু session শেষে error analysis একটু উন্নত হতে পারে।

Acceptance criteria:

• একটি extra space পুরো বাক্যকে ভুল দেখাবে না।
• একটি missing character-এর পরে feedback recover করতে পারবে।
• Combining sequence মাঝপথে থাকলে final error বলা হবে না।
• Correction-এর পর পুরোনো ভুলের accounting consistent থাকবে।
• Lesson completion ভুলভাবে trigger হবে না।

১৭. Weak-character recommendation-এ statistical সতর্কতা দরকার

README-তে weak-character recommendation-এর উল্লেখ আছে। কিন্তু implementation দেখা হয়নি। এখানে শুধু error count দিয়ে দুর্বলতা নির্ধারণ করা যথেষ্ট নয়। README

ধরা যাক একটি character শিক্ষার্থী ২০০ বার লিখেছেন এবং ১০ বার ভুল করেছেন। আরেকটি character একবার লিখে একবার ভুল করেছেন। দ্বিতীয়টির error rate বেশি, কিন্তু evidence অত্যন্ত কম।

Recommendation engine-এর উচিত অন্তত বিবেচনা করা:

• Exposure count
• Error rate
• Recent performance
• Correction latency
• Layout
• Context
• Sample size

একই character standalone অবস্থায় সহজ, conjunct-এর মধ্যে কঠিন হতে পারে। তাই root consonant-level দুর্বলতা আর conjunct-sequence দুর্বলতা এক করে ফেললে ভুল lesson recommend হবে।

উন্নত feedback-এর উদাহরণ: “এই key sequence-এ আরও অনুশীলন দরকার”। প্রমাণ কম হলে “আপনি এই অক্ষরে দুর্বল” ধরনের চূড়ান্ত ভাষা ব্যবহার করবেন না।

শেখানোর software-এ ভুল আত্মবিশ্বাস যেমন ক্ষতিকর, তেমনি ভুল নেতিবাচক feedback-ও ক্ষতিকর।

১৯. Test coverage আছে, কিন্তু গুরুত্বপূর্ণ জায়গা তার বাইরে

এতে src/app এবং src/components এই coverage collection scope-এর অন্তর্ভুক্ত নয়। ওই জায়গায় test নেই, তা বলা যাচ্ছে না; কিন্তু configured coverage percentage ওই অংশগুলোর পূর্ণ মানচিত্র নয়। Jest configuration

১৯.১ কী উন্নত করা উচিত

Coverage strategy module risk অনুযায়ী সাজান:

• Security-critical logic: unauthorized এবং forbidden branch-এর explicit test।
• Typing engine: Unicode edge case এবং state transition test।
• API boundary: validation, authentication এবং ownership test।
• Persistence: retry এবং duplicate-submission test।
• UI behaviour: composition, focus এবং accessible interaction test।

শুধু file count বাড়িয়ে coverage denominator বড় করলেই quality বাড়ে না। আবার critical directory বাদ রেখে সুন্দর percentage দেখানোও যথেষ্ট নয়।

১৯.২ Lines-only threshold-এর সীমা

বর্তমান configuration-এ global line threshold 80 দেখা গেছে। Branch, function বা statement threshold ওই configuration-এ নেই। Line coverage ৮০% মানে authorization-এর সব branch পরীক্ষা হয়েছে নয়। Jest configuration

একটি line execute হলেও তার সত্য এবং মিথ্যা দুই condition পরীক্ষা নাও হতে পারে।

সুপারিশ: প্রথমে critical branch-এর test লিখুন। তারপর সেই বাস্তব baseline অনুযায়ী branch threshold যুক্ত করুন। কেবল সংখ্যা বাড়ানোর জন্য অর্থহীন assertion যোগ করবেন না।

• Owner identity authenticated context থেকে নেওয়া।

২৯. Session save এবং retry-তে idempotency দরকার

এটিও implementation যাচাইয়ের বিষয়।

একজন ব্যবহারকারী practice শেষ করলেন। Network timeout হলো। Frontend আবার submit করল। যদি backend দুবার session record তৈরি করে, তাহলে daily count, average speed এবং certificate eligibility সব ভুল হতে পারে।

Idempotency এমনভাবে design করুন যাতে একই completed session-এর retry নতুন achievement তৈরি না করে।

প্রয়োজনীয় behaviour:

• এক session-এর stable submission identifier।
• Database uniqueness constraint।
• Duplicate request-এ predictable response।
• Partial failure থেকে recover করার নিয়ম।
• Client-এ pending/saved/failed state আলাদা।

“Save failed” দেখিয়ে data আসলে save হয়ে গেলে user আবার submit করবেন। তাই request timeout এবং database failure এক জিনিস ধরে নেওয়া যাবে না।
